# Wb_planner: планировщик поставок и закупок для Wildberries

Скрипт на Python, который каждый день забирает данные из API Wildberries (заказы, продажи, остатки FBO и FBS) в PostgreSQL, считает по каждому товару, размеру и региону спрос и запас в днях и подсказывает селлеру:

- где **дефицит** и **излишек**;
- что **перераспределить** между своими складами (FBS);
- куда **направить следующую поставку** (FBO) и куда не отправлять;
- сколько **заказать на производстве на следующий месяц** с учётом процента выкупа.

Результат выводится в Google Sheets: один сводный лист для сотрудника, который принимает решения о закупке и поставках.

> Проект обезличен: идентификаторы таблицы, складов и токенов удалены, названия и параметры нужно подставить под свой магазин. Публикуется с разрешения заказчика.

## Зачем

Складские системы и сервисы аналитики обычно усредняют остатки по всем размерам и складам. В результате ходовые размеры (M, L) уходят в дефицит, а редкие (XS, 3XL) месяцами лежат на складе. Планировщик считает запас отдельно по каждому размеру и региону, поэтому видно, где реально не хватает товара, а где замороженные деньги.

## Как это работает

```
WB API  ──►  collect  ──►  PostgreSQL  ──►  report  ──►  Google Sheets
(карточки, заказы,         (история,        (спрос, запас в днях,   (лист «Сводка»,
 продажи, остатки)          снимки)          перемещения, заказ)     лист «Состояние»)
```

1. **collect** запрашивает у WB карточки товаров, заказы, продажи, остатки на складах WB (FBO) и на складах продавца (FBS) по всем подключённым кабинетам и складывает данные в PostgreSQL. При первом запуске подтягивается история за 90 дней.
2. **report** по данным из базы считает:
   - **спрос** за выбранное окно (по умолчанию 30 дней);
   - **запас в днях** = остаток / спрос в день, по каждому товару, размеру и региону;
   - **статус**: дефицит (запас меньше 14 дней), норма, излишек (больше 60 дней), нет спроса;
   - **ABC-класс** по доле в заказах (A ≈ 80 % заказов, B ≈ следующие 15 %, остальное C);
   - **перемещения** между складами: из регионов с излишком в регионы с дефицитом, не опуская запас донора ниже 30 дней и не предлагая перемещений меньше 5 штук;
   - **рекомендации по поставкам**: если дефицит остаётся после перемещений, куда направлять поставку на склады WB, где излишек, туда не отправлять;
   - **заказ на следующий месяц**: чистый спрос с учётом процента выкупа × горизонт (месяц + запас 14 дней) минус всё, что уже есть и едет (остаток, возвраты, «от клиента»), раскладка по регионам пропорционально заказам.
3. Результат записывается в Google Sheets пакетно.

## Источники данных (WB API)

| Данные | API |
|---|---|
| Карточки товаров | Content API (`/content/v2/get/cards/list`) |
| Заказы и продажи | Statistics API (`/api/v1/supplier/orders`, `/sales`) |
| Остатки на складах WB (FBO) | Seller Analytics API (stocks-report) |
| Остатки на складах продавца (FBS) | Marketplace API (`/api/v3/stocks/{warehouse}`) |

Лимиты WB учитываются: при ответе 429 скрипт ждёт время из заголовка `X-Ratelimit-Retry`, а при его отсутствии повторяет запрос с нарастающей паузой (до 6 попыток); между запросами делается пауза по заголовкам `X-Ratelimit-Remaining` и `X-Ratelimit-Reset`.

## База данных (PostgreSQL)

Таблицы создаются командой `init`: `skus`, `barcodes`, `stock_snapshot` (ежедневные снимки остатков), `orders`, `sales`, `transit_snapshot`, `recommendation`, `order_plan`, `sheet_snapshot`, `run_log` (журнал каждого шага: статус, число строк, ошибка). Уникальные ключи (`srid`, `sale_id`, составные ключи на снимки) защищают от дублей при повторных загрузках.

## Настройки

Основные параметры в начале файла:

| Параметр | Значение по умолчанию | Смысл |
|---|---|---|
| `DEMAND_WINDOW_DAYS` | 30 | окно расчёта спроса (меняется в таблице на листе «Настройки анализа») |
| `TARGET_COVER_DAYS` | 30 | нормальный запас, дней |
| `DEFICIT_DAYS` / `SURPLUS_DAYS` | 14 / 60 | границы дефицита и излишка |
| `DONOR_KEEP_DAYS` | 30 | сколько дней запаса оставить на складе-доноре |
| `MIN_TRANSFER_QTY` | 5 | минимальное перемещение, шт. |
| `ORDER_HORIZON_DAYS`, `SAFETY_DAYS` | 30, 14 | горизонт заказа и страховой запас |
| `BUCKETS` | ЦФО, ЮФО, Казань, Екатеринбург, Новосибирск, Красноярск | региональные группы складов |
| `DRY_RUN`, `TEST_MODE` | выкл. | запуск без записи в таблицу / на нескольких артикулах |

Секреты берутся из переменных окружения (файл `.env`): `WB_TOKEN_1`, `WB_TOKEN_2` (по одному токену на кабинет), `DATABASE_URL`, `GOOGLE_SERVICE_ACCOUNT_FILE`. В репозитории их нет.

## Запуск

```bash
pip install numpy pandas requests psycopg2-binary python-dotenv gspread google-auth
python wb_planner_cleaned.py init      # создать таблицы в базе
python wb_planner_cleaned.py collect   # собрать данные из WB API в PostgreSQL
python wb_planner_cleaned.py report    # посчитать и записать в Google Sheets
python wb_planner_cleaned.py all       # collect + report
```

Нужны: PostgreSQL, сервисный аккаунт Google с доступом к таблице, токены WB с правами на статистику, аналитику, контент и маркетплейс.

## Что здесь можно улучшить

- Вынести настройки (регионы, склады, пороги) из кода в конфигурационный файл.
- Разбить один файл на модули (сбор данных, расчёты, запись) и покрыть расчёты тестами.
- Добавить расписание (cron/планировщик) и оповещения при ошибках шага.

Python, PostgreSQL (psycopg2), Pandas/NumPy, Requests, gspread (Google Sheets API), WB API.
